What lives where — and what happens if it goes down

Rule: nothing that cannot be rebuilt lives only in Redis. The job document is in Mongo; the queue carries just the jobId.

Redis — coordination

What Detail If Redis goes down
Bull queue custeio-jobs Payload { jobId }; the job document lives in Mongo. No enqueueing or consuming. Jobs already written to Mongo are not lost.
Rate limit Fixed window per (scope, IP), key rate:<scope>. 2 s timeout. Fails open — requests pass; the operator has to watch the rate-limit redis error log.
Liveness Health probe PING, worker heartbeat, queue-depth sampling (every 60 s). The /health/ready probe returns 503.

Sessions are not in Redis: NextAuth uses the JWT strategy, so the session is the authjs.session-token cookie.

The jobs: two exist, four are the product

Every asynchronous execution is a row in jobs + a Bull entry. Adding a kind touches four places (type, payload schema, handler registry, creation route); a test fails if the tables drift apart.

Life of a job

1
Create the document in jobs (queued) and enqueue { jobId }.
2
Worker validates the payload against jobPayloadSchemas[kind] and calls the registry handler.
3
Write logs, result and progress.timings; a permanent failure (PermanentJobError) is not re-enqueued.
4
Failed? Exponential retry for jobs with more than 1 attempt (APP_BULL_*); the operator can re-enqueue from the page — audited as job.retry.

Why the webhook only enqueues

Alloy allows 3 seconds to answer and disables the webhook after many invalid answers. The route validates authenticity, writes the Job, enqueues and answers {"status":"ok"}; the heavy work (stock debit) runs in the worker. Duplicated events are absorbed by the unique index (storeId, externalOrderId) on Orders.

Data flow: a purchase credits, a sale debits

The heart of the product. Two halves that meet in RawIngredients: the purchase moves the average cost; the sale consumes it and fixes the order's real CMV.

Half 1 — sefaz.nfe.received (credits)

1
Downloads the full NFe XML (after manifesting Ciência da Operação) and checks ProcessedInvoices by access key.
2
For each det/prod: looks up SupplierItemMappings by (store, issuer CNPJ, cProd).
3
No match → pending manual mapping (no AI in the MVP). Match → converts and rolls the average cost:
convertedQty = qCom × conversionFactor
newAverageCost = (currentStock × averageCost + vProd) / (currentStock + convertedQty)
newCurrentStock = currentStock + convertedQty

Uses vProd (the line total) directly so it does not round twice.

Half 2 — pos.order.received (debits)

1
Idempotency: unique index (storeId, externalOrderId); reprocessing an order is a no-op.
2
Resolves each item in PartnerProducts by (store, externalId).
3
Aggregates the recipe: recipe × quantity + each add-on's modifier.recipe.
4
Debits each ingredient atomically (findOneAndUpdate with a negative $inc) and reads averageCost from the same returned document — no second query, no race with a purchase.
5
Writes the Order; if currentStock < minAlertStock (and > 0), enqueues the alert.
calculatedCost = Σ (debited qty × averageCost read)
profitMargin = (totalValue − calculatedCost) / totalValue

Decisions already made

  • Stock may go negative. It is a sign of an unrecorded purchase or a wrong recipe — a discrepancy datum, not an error that blocks a sale.
  • A sale with no recipe writes calculatedCost = 0, margin 1; the dashboard flags it later.
  • No AI in the mapping for the MVP: manual mapping.
  • CMV is written at sale time and never recalculated.

Still open

  • Where an NFe line with no mapping becomes visible to the owner (ProcessedInvoices only holds the header).
  • The real Alloy order payload, and whether an add-on can have quantity > 1.
  • Order of “insert Order → debit” vs. “debit → insert”, so an attempt that fails to write the order does not debit stock.
  • The first sale of a never-bought ingredient has an artificially perfect CMV (averageCost = 0).

Multi-tenancy, secrets and limits

Cliente → Loja → domain data. Each credential lives where its natural scope lives.

Hierarchy and scope

Cliente (tenant, who pays)

Organization

Users (Users.organizationIds), billing (Asaas), status onboarding · active · suspended · canceled, invite link.

↓ 1 : N
Loja (1 CNPJ ↔ 1 POS account)

Store

CNPJ unique in the system, provider, externalId, apiKey (write-only), whatsappNumber.

↓ 1 : N
Domain — always by storeId

RawIngredients · PartnerProducts · SupplierItemMappings · ProcessedInvoices · Orders

Rule: every read and write is scoped by the validated id — getAuthorizedOrganizationIds only narrows, never widens. Access to /system/* is Users.systemLevel alone; there are no groups or roles.

Secrets

Secret Where it lives State
Stores.apiKey (Alloy store token) Mongo, AES-256-GCM with a random IV; key in APP_SECRETS_ENCRYPTION_KEY; never returned to the client exists
ALLOY_INTEGRATOR_TOKEN Environment variable — one value for the whole installation, not per store exists
e-CNPJ A1 (.pfx + password) Direction discussed: .pfx in Blob and the password in a different trust boundary (e.g. Key Vault); not decided open
Webhook signature (Alloy, Meta) To be defined per provider; Alloy only documents a callback URL and a {"status":"ok"} answer open

The e-CNPJ leaks worse than any other credential: it lets someone sign tax documents on the client's behalf, not just read. We investigated Procuração Eletrônica to avoid custody — the SEFAZ webservice does not consult it; holding each store's A1 remains the design.
