# Alloy API — technical mapping

Mapping of the routes, authentication and webhooks of the Alloy (POS) API, gathered from the public
help center and the Postman collections Alloy publishes. This document is the technical reference
used to implement the `pos.catalog.sync` and `pos.order.received` jobs described in
`CLAUDE.md`. See also [POS providers](./pos-providers.md) for the context on
why only Alloy is confirmed as integrable today.

> Researched on 2026-09-17 from public documentation + validated against the real account the same
> day (see [Validated connection](#validated-connection) below). The exact webhook payload has not
> been confirmed yet — only the REST catalog call has been tested so far.

## How to get access (step by step)

Alloy separates two kinds of credential. **We need both** for Custeio to work:

1. **Developer token (`integrador-token`)** — identifies Custeio as an integrator to the Alloy
   platform as a whole. It is **unique per integrator**, not per store.
   - Open the "Developer area" in the panel of the account we already use and generate the token.
     **Confirmed 2026-09-24:** on the "loja piloto" account this was available immediately,
     with no support ticket. (The support-ticket route in Alloy's help center may still apply to
     accounts where the area is not enabled.) A **test store** also comes with it, to validate the
     integration without touching real data.
   - Generating a new token invalidates the previous one — be careful if regenerating after
     already being in production.
2. **Store token (`Token da loja`, sent as a `Bearer` header)** — per **store/CNPJ** (each `Store`
   in Custeio has its own). Generated by the store owner under **Integrações → API** in the
   regular Alloy panel (the operational one, not the developer one).

Since we already have the login/password of the Alloy account (paid plan), the practical step is:
generate the developer token in the developer area and the store token under Integrações → API.

### Architecture implication

`app/models/stores.ts` already reserves `externalId` + `apiKey` per store — that maps directly to
the **store token**. The **`integrador-token`** is different: it is a single value for the whole
Custeio installation (it does not vary per `Store`), so it becomes a system environment
variable/secret (`ALLOY_INTEGRATOR_TOKEN`, already in `app/lib/env.ts`), not a field on `Stores`.

## Authentication

Headers sent on (almost) every call to the Delivery, Catalog and On-site Service APIs:

```
Bearer: {{store token}}
integrador-token: {{integrador-token}}
```

(The header name is literally `Bearer` in the official exported collection — but we tested it and
the API also accepts the standard `Authorization: Bearer {{store token}}`. Either works; we will
use `Authorization` in the client because it is the HTTP standard.)

The **Marketing & Loyalty** API uses a separate scheme: a login with email/password
(`POST /api/auth/login`) returns an `access_token`, later used as
`Authorization: Bearer {{access_token}}` — in addition to the `integrador-token`, which remains
mandatory on every call.

**Base URL:** `https://api.alloy.al/api/...` — **confirmed** on 2026-09-17. `{{host}}` is not
exposed anywhere self-service in the Alloy API itself (the **Integrações → API Alloy** screen of
the partner panel only shows the token; the "API Documentation" link there points to the same
Postman that does not resolve `{{host}}`). The value came by inference from another screen of the
same panel — **Integrações → API · Order application (Open Delivery)** — which shows the base URL
`https://api.alloy.al/api/opendelivery`. We tested `https://api.alloy.al/api/catalog/getproducts`
with the real token of the "loja piloto" organization and it came back `200` with the real
catalog — host confirmed.

**Standard error codes** (documented in every collection):

| Code | Meaning                       |
| ---- | ----------------------------- |
| 400  | Error in the information sent |
| 401  | Authentication failed         |
| 429  | Request limit exceeded        |

> **Do not trust the HTTP status alone.** A rejected _store token_ comes back as **HTTP 200** with an
> error body (see [Behaviors verified on 2026-09-24](#behaviors-verified-on-2026-09-24)). Always
> check the body for `status: "error"` before treating a call as successful.

## Validated connection

Tested on 2026-09-17 with `GET /api/catalog/getproducts`, headers `Authorization: Bearer
<store token>` + `integrador-token: <ALLOY_INTEGRATOR_TOKEN>`, against the "loja piloto"
organization (real data, not a test store). Result: `200 OK` with the full catalog.

**Measured rate limit — much tighter than anything publicly documented:**

- `x-ratelimit-limit: 2`, `x-ratelimit-remaining` decrements per call.
- Once exhausted, the API answers `429` until the end of the window.
- Window confirmed by measurement: under 10s was **not** enough to reset; **65s was**. That is,
  it is **2 requests per minute per store token** (not per integrator — the limit is scoped to the
  `Token da loja`, so each `Store` has its own quota of 2/min).

**Direct implication for the jobs' design:**

- `pos.catalog.sync` cannot run on a short interval or retry aggressively — it is 1 `getproducts`
  call per sync, so the interval between syncs of the same store should sit well above 1 minute
  (e.g. every few hours, or on manual demand).
- **Polling `getorders`** as the main strategy is ruled out — 2 calls/min barely covers one query
  every 30s, and leaves 0 quota for `changestatus` in the same minute. **The webhook becomes
  mandatory, not optional**, for `pos.order.received`; `getorders` is reserved for sporadic
  reconciliation (e.g. at worker boot, or once an hour) and `getListWebhookFailedEvents` to recover
  what the webhook missed.
- Any `429` retry in the HTTP client needs a backoff of at least ~60s, not the seconds/short
  exponential we use in other integrations.

> Since **2025-06-01** the `integrador-token` is **mandatory** on all integrations (the
> documentation says "until 2025-06-01 it will be necessary" — that date has passed, so today it
> is an active requirement, not a future window).

## Behaviors verified on 2026-09-24

Measured with read-only calls to `GET /api/catalog/getproducts` (the real store token of the "loja piloto"
account and deliberately invalid ones). None of them changed data.

| Situation                                       | Response                                                                                             |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Invalid / random store token + valid integrator | **HTTP 200**, body `{"status":"error","code":"400","message":"Token da loja informado é inválido."}` |
| Valid integrator token, no `Bearer` at all      | Same as above — the store token is what is checked, the call is not rejected at HTTP level           |
| Missing `integrador-token`                      | HTTP 401                                                                                             |
| Real store token, quota spent                   | HTTP 429, body `{"status":"error", "message":"Too many requests."}`, no `Retry-After`                |
| `GET /api/tokenInfo` with an invalid token      | HTTP 302 redirect to `parceiros.alloy.al/login` (HTML) — not usable as a health probe                |

**Rate limit buckets.** A real store token gets `x-ratelimit-limit: 2` and returns 429 on the third
call inside a minute. While that bucket was at 0, a call with a _different_ bearer and the same
integrator token still got a fresh bucket (`limit: 1000`). So the quota is **keyed by the store
token**; the `integrador-token` is **not** a bottleneck shared between stores, and a per-customer
developer token would not add headroom. (Invalid tokens fall into a separate 1000-request bucket,
which is why an invalid key looks "healthy" if only the headers are read.)

### How Custeio handles this

- `testAlloyConnection` (`app/lib/alloy-client.ts`) parses the body and fails on `status: "error"`
  or a non-JSON body, storing Alloy's message in the store's `lastError`.
- A `429` sets `rateLimited: true` on the result. It means the token is valid and only the quota is
  spent, so the store's status is **left untouched** and the API answers `429` to the UI.
- `reserveAlloyRequest(storeId)` (`app/lib/alloy-rate-limit.ts`) budgets **2 requests/minute per
  store** in Redis (fixed 60s window, fail-open if Redis is down). "Testar conexão" reserves before
  calling Alloy. Every future Alloy call for a store (`pos.catalog.sync`, `pos.order.received`,
  reconciliation) must go through it so they share one budget — the health check spends 1 of the 2.
- Our window is fixed and Alloy's may not be aligned with it, so a `429` from Alloy can still occur
  at the edges and must still be handled.
- `pos.catalog.sync` is implemented (`app/lib/services/catalog-sync.ts`): one `getproducts` request
  per run, reserved through `reserveAlloyRequest` first; a spent budget or a 429 fails the run as
  retryable (3 attempts, 65 s apart). See [Products](./products.md).

### `getproducts` payload (measured 2026-09-26)

`{ status: "success", code: "200", produtos: [...] }` — despite the name, `produtos` are
**categories** (`id`, `nome`, `status`, `is_hidden`, `items[]`). Each item carries `id`, `nome`,
`preco` and `preco_promocional` (**strings**, `"59.50"`), `status_promocao`, `status`, `cod_pdv`,
`categorias_de_complemento[]`, each with `complementos[]` (`id`, `nome`, `preco`, `status`,
`cod_pdv`). One request returns the whole menu (a real store: 82 items in 7 categories, 843
complements, ~470 KB), so `getitem` per product is never needed.

Things the sample showed that shape the model:

- **`cod_pdv` is not unique** (62 items, 32 distinct codes) — the item `id` is the key.
- **Complements are copied per item**: 843 rows with 843 distinct ids but 45 distinct names.
- **Half the items are inactive**: categories such as "itens integração ifood" come with
  `status: 0, is_hidden: 1`. An item is sold only if the item, its category and the category's
  visibility all say so (39 of 82 here).
- A `status_promocao: 1` can come with `preco_promocional: "0.00"` — not a real promotion.
- The saved sample is real business data: keep it outside git.

## The 5 APIs

Source: the official Postman collections (Documenter link in parentheses). All return JSON.

### 1. Product catalog (`/api/catalog/*`)

[Postman](https://documenter.getpostman.com/view/569841/Uyxbq9W6) — used by the
`pos.catalog.sync` job.

| Method   | Route                                                                                                                          | Description                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| GET      | `getproducts`                                                                                                                  | Lists all the store's items and their settings — the main endpoint for catalog sync |
| GET      | `getitem?item_id=`                                                                                                             | A specific item, with its add-on category and nested add-ons                        |
| POST     | `edititem` / `createitem` / `deleteitem`                                                                                       | Item CRUD                                                                           |
| POST     | `edititemdisponibility`                                                                                                        | Turns an item's availability on/off                                                 |
| GET      | `getcategorie?categoria_id=`                                                                                                   | A specific category                                                                 |
| POST     | `editcategorie` / `createcategorie` / `deletecategorie`                                                                        | Category CRUD                                                                       |
| POST     | `editcategoriedisponibility`                                                                                                   | Turns a category's availability on/off                                              |
| GET      | `getcategorieofcomplement?categoria_id=`                                                                                       | An add-on category (e.g. "Choose the meat doneness")                                |
| POST     | `editcategorieofcomplement` / `createcategorieofcomplement` / `deletecategorieofcomplement`                                    | Add-on category CRUD                                                                |
| GET      | `getcomplement?complemento_id=`                                                                                                | A specific add-on                                                                   |
| POST     | `editcomplement` / `createcomplement` / `deletecomplement`                                                                     | Add-on CRUD                                                                         |
| GET/POST | `getitemimages`, `createitemimage`, `edititemimage`, `deleteitemimage`                                                         | Item images                                                                         |
| GET/POST | `getcategoriecover`, `editcategoriecover`                                                                                      | Category cover                                                                      |
| GET/POST | `getstoresugestions`, `additemsugestion`, `removeitemsugestion`                                                                | Item suggestions in the store                                                       |
| GET/POST | `getstorehighlightscovers`, `editstorehighlightscovers`, `getstorehighlightsconfiguration`, `editstorehighlightsconfiguration` | Store highlights                                                                    |

The key field for the recipe mapping: `cod_pdv` in `getitem`/`getproducts` — the likely link point
between `PartnerProducts` and the real item in the POS.

### 2. Delivery & Pickup (`/api/delivery/*`)

[Postman](https://documenter.getpostman.com/view/569841/TzeXmntp) — the most relevant for
`pos.order.received`.

| Method | Route                              | Description                                                                                                                                                                                                              |
| ------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `getorders`                        | Lists orders. Filters by status (`realizado`, `producao`, `pronto`, `finalizado`, `cancelado`) and `data_atualizacao`. **Without a status filter it returns only pending ones; without a date, only the current day's.** |
| POST   | `changestatus?pedido_ref=`         | Moves the order to the next status in the flow (Pending → In production → Ready → Finished; or Scheduling accepted → In production when scheduled)                                                                       |
| POST   | `cancelaPedido?pedido_ref=`        | Cancels an order                                                                                                                                                                                                         |
| GET    | `getlistpaymentsmethods`           | Lists the available payment methods                                                                                                                                                                                      |
| POST   | `sendToMotoboyService?pedido_ref=` | Triggers the motoboy service for the order                                                                                                                                                                               |
| GET    | `getListWebhookFailedEvents`       | Lists webhook events that failed to deliver — **the list is erased after being queried once**, i.e. it is a "collection" queue of lost events, not a history                                                             |

`getorders` returns the full order: `ref`, `total`, `status` (int), `meio_de_pagamento`, user,
delivery address and items with add-ons — that is the structure we will use for the fractional
stock deduction through `PartnerProduct.recipe`.

The official flow Alloy recommends (documented in the collection itself) is **polling**, not pure
webhook:

1. Query pending orders periodically.
2. Advance the status to "confirmed" on receipt.
3. Advance again when the order is ready.
4. Repeat the query periodically.

This suggests that, even though a webhook exists, Alloy expects the integrator to also poll as a
safety net — which matches the existence of the `getListWebhookFailedEvents` endpoint.

### 3. On-site Service / Digital Menu in the Store (`/api/cardapiodigital/*`)

[Postman](https://documenter.getpostman.com/view/569841/TzmCfs4b) — orders placed through the QR

| Method | Route                                                             | Description                                                                  |
| ------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| GET    | `getorders`                                                       | On-site orders (same status filters as delivery, without `data_atualizacao`) |
| POST   | `changestatus?pedido_ref=`                                        | Same status flow as delivery                                                 |
| POST   | `cancelaPedido?pedido_ref=`                                       | Cancels an order                                                             |
| GET    | `listQrCodes` / `getQrCode?codPdv=`                               | Lists/queries QR codes (tables)                                              |
| POST   | `createQrCode` / `deleteQrCode`                                   | QR code CRUD                                                                 |
| POST   | `fechaMesa?codPdv=&forma=`                                        | Closes the table's bill with the payment method                              |
| POST   | `liberaComanda` / `bloqueiaQrcode` / `desbloqueiaQrcode`          | Tab/QR code control                                                          |
| POST   | `transferirPedidos?cod_pdv_origem=&cod_pdv_destino=`              | Transfers orders between POS units (tables)                                  |
| GET    | `getNotifications` / POST `dismissNotification?cod_notification=` | The store's internal notifications                                           |
| GET    | `getlistpaymentsmethods`                                          | Payment methods                                                              |

### 5. Order Registration (external → Alloy)

There is no public Postman collection — it is **access under manual approval**, through a form at
`https://assistente-criativo.meajuda.cc/api/cadastro-pedidos`. It serves the **inverse** case of
what Custeio needs: registering orders from an external system **into** Alloy (e.g. a
marketplace sending an order to the POS). **Not needed for the MVP** — Custeio only consumes
sales that were already born in Alloy, it does not create orders there.

## Webhooks

The public documentation ([source](https://ola.meajuda.cc/extras/api-de-integracoes/notificacoes-e-eventos-webhook))
is shallow — it lists neither the event catalog nor the payload format. What is confirmed:

- The callback URL is registered under **Integrações** in the Alloy panel (not through the API).
- An event fires when "a change occurs in a resource's state" — e.g. a new order.
- **Response timeout: 3 seconds.** If exceeded, Alloy resends after 5 minutes.
- The expected response from our endpoint: `{"status": "ok"}`. Many invalid responses in a row
  **disable the webhook automatically**.
- Events can arrive duplicated — the consumer has to be idempotent (which matches the `Jobs` +
  `correlationId` pattern we already use).
- Alloy's own recommendation: enqueue the event and process it later, asynchronously — exactly the
  Bull pattern the `pos.order.received` job is going to follow.
- There is a fallback route (`GET /api/delivery/getListWebhookFailedEvents`) to recover events that
  failed to deliver, which suggests a webhook alone is not 100% reliable and `getorders` polling
  should keep existing as a safety net.

**Probe of `getorders` (2026-10-02, `scripts/dev/alloy-sample-orders.ts`)**: two calls against the
"loja principal" store — `status=finalizado` with no date, and with `data_atualizacao=2026-09-25` —
both answered `{"status":"success","code":"200","pedidos_count":0,"pedidos":[]}`. So the auth and
route are right, but no order shape was captured yet: either that store has no finalized orders in
the window, or the `data_atualizacao` format is wrong. Next: try another status/date, or capture a
real webhook event.

**The exact order-event payload**: not publicly documented. We will only confirm the real format by
registering a test URL (e.g. a temporary endpoint on `webhook.site`) on the test store of the
developer panel, once we have access.

## Confirmed webhook payload (captured 2026-10-02)

Captured on the Loja Piloto store through a temporary `webhook.site` endpoint (the sample below is
**sanitized**: no customer name, phone, address or CPF; the real payload carries all of them, so
Custeio must persist only the fields it needs).

**Registration (Integrações → Webhooks).** Fields: URL, description, **Chave**, order events ("Novo
pedido", "Alteração de status do pedido"), optional marketplaces to exclude (iFood, DiDi Food), menu
events. **On creating, Alloy POSTs `{}` to the URL and requires a valid JSON answer
(`{"status":"ok"}`)**; an empty answer fails with "Endpoint inválido, ou com resposta incorreta.
Resposta recebida: null". Deliveries come from changing AWS São Paulo IPs (seen: `52.67.132.46`,
`54.207.30.64`), user-agent `GuzzleHttp` — **do not allow-list by IP**. The **Chave** is sent as
`Authorization: Bearer <chave>` **and** as `chave` in the body: validate it on every call.

**Envelope** (event `alteracao_de_status`; a "Novo pedido" event was not captured yet):

```json
{

  "modulo": "loja_delivery",
  "data": "2026-10-02",
  "chave": "<chave>",
  "loja_id": 18424,
  "pedido_ref": 1521,
  "novo_status": 3,
  "dados_pedido": {
    "ref": 1521,
    "status": 3,
    "created_at": "2026-10-02 19:11:06",
    "aceito_em": "...",
    "producao_em": "...",
    "transito_em": "...",
    "entregue_em": null,
    "total": 50.4,
    "valor_entrega": 3,
    "valor_desconto": 0,
    "total_com_descontos": 53.4,
    "delivery": 1,
    "retirada": 0,

    "itens": [
      {
        "quantidade": 1,
        "valor": 15,
        "unidades": "1.000",
        "cod_pdv": "283",
        "nome": "João Smash",
        "descricao": "Pão brioche, blend Angus smash 100g, ...",
        "categoria": "Hambúrguer Artesanal",
        "complementos": [
          {
            "quantidade": 1,
            "valor": 0,
            "cod_pdv": "575",
            "nome": "Ao Ponto",
            "categoria": "Ponto da carne"

            "categoria": "Batata Frita Extra"
          }

```

What it settles:

- **`loja_id` (18424) is the Alloy store id** — the value `Stores.externalId` should hold (the field
  is immutable after creation, so a wrong value needs a deliberate fix). It lets the webhook be
  matched to a Store.
- **`ref` / `pedido_ref`** (1521) is the order reference, the same number the history report prints as
  `#1521` → candidate `externalOrderId`.
- **Items carry `cod_pdv`, not the catalog `id`.** `cod_pdv` is **not unique among catalog items**
  (83 items, 33 codes; e.g. `266` = two "Golias Burguer + Fritas" copies). The same code repeats
  for the same real product across channels, so **`cod_pdv` is the identity of the product**, not
  of the catalog row: model the recipe per `cod_pdv`.
- **Complements carry `cod_pdv`, and it is shared across products** ("Ao Ponto" is `575` under every
  burger, "Molho da Casa" `192`, "Fritas Combo" `802`, "Sem Molho" `553`, "Fritas Extra" `152`),
  unlike the catalog complement ids, which are per item. A complement recipe can therefore be
  defined once per `cod_pdv`. The catalog sync stores it as `PartnerProducts.modifiers[].codPdv` (since 2026-10-02; existing
  rows get it on the next "Sincronizar cardápio").
- Each complement has its own `quantidade` and `valor`. **A zero price does not mean no
  consumption** ("Molho Verde" is R$ 0 and uses sauce); consumption comes from the complement's
  recipe. A paid complement ("Blend Angus (100g)", R$ 6) is an extra patty.
- **Fries can arrive as a complement** ("Fritas Combo", R$ 0) of a "… + Fritas" product, so fries
  are not necessarily in the product recipe.
- **iFood orders** come through the same webhook, with `id_provedor: 1`, the items in the category
  "itens integração ifood" (complements in "complementos integração ifood") **using the same
  `cod_pdv`**, plus an `ifood_dados` block (`id_externo`, `ifood_display_id`) and the coupon in
  `codigo_desconto`/`valor_desconto`. Payment is split in `meios_de_pagamento` (e.g. card + "Incentivo
  iFood").
- **Money fields**: `total` is the items (plus iFood's extra fee, which shows up in `obs`),
  `valor_entrega` is separate, and `total_com_descontos = total − valor_desconto + valor_entrega`.
- **Item descriptions state the recipe** (e.g. "Casa Burguer + Fritas": "blend Angus de 150g" — the
  owner said 160 g; to confirm), useful when writing the technical sheets.
- `novo_status: 3` is "em trânsito" (dispatched, `transito_em` set). The other status codes are not
  mapped yet.

**The "Novo pedido" event (captured 2026-10-02 19:52:14)** has a **different envelope**: the order
sits under `pedido` (not `dados_pedido`) and there is no `pedido_ref`/`novo_status` —
`{ "evento": "novo_pedido", "modulo": "loja_delivery", "data", "chave", "loja_id", "pedido": { ... } }`.
The order body is the same as in `dados_pedido` (`ref`, `status`, `itens[]` with `complementos[]`, totals,
payment), so **a reader must accept both envelopes**. The status event followed 10 seconds later
(the store auto-accepts), also with the full items: either event alone carries enough to compute
consumption, so the debit needs its own "already debited" marker on top of the `(storeId, ref)` key.

Statuses seen in `status`/`novo_status`: **1 = new**, **2 = accepted / in production**
(`aceito_em`, `producao_em` set), **3 = in transit** (`transito_em` set). Delivered and cancelled
codes are not captured yet. Meat-doneness complements have one code per doneness ("Ao Ponto" `575`,
"Bem Passado" `574`) and consume nothing.

Still unknown: the cancellation event and status code, the delivered status, and whether 99 Food
orders look the same. Which event should trigger the stock debit is an open decision; current
recommendation: debit when the order is accepted (status 2) and reverse on cancellation.

**99Food orders (captured 2026-10-02)** come through the same webhook with **`id_provedor: 43`** and a
`didi_pedido` block (its `pedido_didi_id` is the marketplace order id) instead of `ifood_dados`. Their items
also sit in the category "itens integração ifood", so the channel must be read from `id_provedor`, never from
the item category. They add `valor_adicional` (the marketplace service fee) and a split payment with
"Incentivo 99Food". Extra-sauce add-ons show up as paid complements ("Maionese Defumada Extra" `105`,
"Molho Barbecue Extra" `147`, R$ 2 each, category "Adicionais") and consume ingredient like any other.

**Custeio's receiver** (`POST /api/v1/webhooks/alloy`, `app/lib/services/pos-events.ts`): the "Chave" identifies the
Store by hash (`Stores.webhookKeyHash`, set with `scripts/dev/set-store-webhook.ts`), the delivery is classified
and stored sanitized in `pos_events` (no customer data), repeated deliveries are deduplicated, and the
validation `{}` ping answers `{"status":"ok"}`. It only records: no `Orders` write and no stock debit yet. The
history is the "Eventos do PDV" page (`/system/pos-events`, in the System group); `scripts/dev/seed-pos-events.ts` fills it with sample rows.

**More deliveries (captured 2026-10-02, orders 1523–1532)**, what they settled:

- **Status 4 = delivered** (`entregue_em` set). Sequence for the store's own channel: 1 new → 2 accepted
  (seconds later, auto) → 3 in transit → 4 delivered. **iFood orders arrive already accepted**: the
  `novo_pedido` itself has `status: 2` and `aceito_em == created_at`, and a `alteracao_de_status` with the
  same body follows, so both events can be the first to say "accepted". 99Food goes 1 → 2 in ~16 s.
  A cancellation still was not captured.
- **Quantities multiply**: `valor` is the **unit** price (4 × R$ 27,90 = R$ 111,60) and a complement
  listed once under an item of `quantidade: 4` applies to all four. A complement can also carry its own
  `quantidade` ("Fritas Combo" × 3 inside a combo). Consumption = item quantity × complement quantity ×
  the complement's recipe, summed over every entry — **the same code can be listed several times** in one
  item (the "Combo Pedro, Tiago e João" lists "Bem Passado" and "Molho da Casa" once per burger).
- **Combos** ("Combo Pedro, Tiago e João", cod `287`): the burgers are part of the product (its recipe is the
  three patties); the customer's choices are complements (doneness and sauce per burger, "Fritas Combo" × 3).
- **A product or complement may arrive with an empty `cod_pdv`**: "Ester burger + Fritas + Refri Grátis"
  (category "Promoções") and **all** of its complements came with `cod_pdv: ""`. Those can only be matched by
  name (normalised — "Molho da casa" and "Molho da Casa" both appear), so a recipe keyed only by code
  cannot cover them. Open decision.
- A "free soda chosen by the store" is a complement too ("Refrigerante 200ml", empty code): it consumes a
  soda no one picks in the order.
- **Money**: `total` is the items plus, for iFood, the marketplace fee (shown only in `obs`: "Taxa adicional
  iFood"); 99Food puts its fee in `valor_adicional`. `total_com_descontos = total − valor_desconto +
valor_entrega − valor_desconto_entrega`. "Incentivo iFood/99Food" in `meios_de_pagamento` is the
  marketplace paying the coupon, not the customer. Marketplace commissions are not in the payload.
- **Timestamps** (`created_at`, `aceito_em`…) are naive local time (America/Sao_Paulo), not UTC.
- At `novo_pedido` a 99Food order has `didi_pedido: null`; the block (with `pedido_didi_id`) only shows up in the
  next event.
- **Item descriptions carry the recipe in words** (useful to fill the technical sheets): João Smash — brioche,
  Angus smash 100 g, cheddar, bacon, sauce; Loja Piloto — brioche, Angus 150 g, cheddar, bacon, caramelized onion,
  sauce; Sansão — brioche, 2 × Angus 150 g, cheddar, bacon, caramelized onion, sauce; Rute — brioche, Angus
  150 g, cheddar, lettuce, tomato, caramelized onion, sauce; Ester — brioche, chicken thigh 150 g, **prato
  cheese**, bacon, lettuce, tomato, sauce; Eva — brioche, rib 150 g, **double cheddar**, bacon, lettuce, red
  onion, sauce. The Angus burgers are 150 g (confirmed by the owner); the stock ingredient is "Angus 150 g".

**Third batch (orders 1522–1535, 2026-10-02)**:

- **The same complement arrives with and without its `cod_pdv`**: "Fritas Combo" is `802` on one order and `""`
  on the next ("Ponto da carne" and "Fritas Combo" empty on 1529, 1532, 1535; some products too — the "Combo 2
  Loja Piloto" and "Ester + Refri Grátis" promotions have no code in the catalog either). The debit therefore
  resolves an empty code **by name through the catalog**, only when that name maps to a single code, and a
  product left unresolved falls back to the recipe on the catalog row of that name
  (`services/order-stock.ts`, `loadRecipes`).
- **Counter orders come through this webhook too**: order 1535 has `retirada: 1`, `valor_entrega: 0`,
  `criado_por: <staff id>` and a placeholder customer ("Cliente Não Informado"). `criado_por` set = typed in
  by someone on the team; `retirada: 1` = pickup. Kept as `pickup` / `createdByStaff` in the sanitized order.
- **Item `obs` can change the recipe** and cannot be modelled: "TROCAR POR -> queijo prato" (1529) swaps an
  ingredient; the order `obs` also carries instructions ("Identificar o sanduíche mal passado"). Known blind
  spot of the expected consumption.
- **Combo with its own free soda**: "Refrigerante 200ml" is code `804`, `quantidade: 2` for a combo of two;
  the brand is the store's choice, so its recipe is a generic 200 ml soda. "Fritas Extra (Saquinho)" `152`
  with `quantidade: 2` is paid (R$ 7,50 each): revenue = item + Σ complement price × quantity (105,90 on 1534).
- **Catalog inconsistency found**: "Combo - 04 Sansão + Fritas + Guaraná 1,5 Litros" has "Molho Verde" mapped to
  code `516` and "Maionese Defumada" to `518` — swapped against every other product (`518` / `516`). Orders for
  it would debit the wrong sauce; fix in the Alloy menu.
- Status 4 (delivered) arrived for 1522–1526 with `entregue_em`; replays of earlier events (same body) are
  deduplicated.
